#+title: Inbox Socket Delivery
#+date: 2026-08-24

* Objective

Replace the coordinator relay with a direct write to the target session's inbox
socket. Today Emacs types into a terminal, a Haiku session reads what it typed,
and that session decides where to forward it. Every bug found so far lives in
one of those hops. Posting to the socket removes both.

The spike that gated this work is done. The approach is viable.

* Spike Results

The open question was whether a process outside any Claude session can deliver
at all. It has no ancestry to prove and no token to present, so it might be held
for approval instead.

Conditions were right for the test. Emacs has no =CLAUDE_CODE_MESSAGING_TOKEN=,
no session environment, and its parent is PID 1, so it is definitively outside
every session tree. Frames were written from Emacs itself with
=make-network-process=, which is exactly how the real package would do it.

** It works

A default-mode session received the frame and started a turn on it. The frame
was the minimal form, with no auth line:

#+begin_example
{"type":"user","message":{"content":"..."}}\n
#+end_example

** The receiver identifies the sender by PID

A held message was reported on the receiving side as coming
=from an unidentified session [verified pid 39911]=, which is the Emacs process.
So the absence of a token does not make the sender anonymous.

** Holding is real, and the sender cannot see it

A session with =crossSessionInbound= set to =hold= did not act on the message.
It told its own user clearly, naming the setting and the remedy. Emacs was told
nothing.

Every outcome looks the same from the sending side:

- delivered :: socket closes, zero bytes back
- held :: socket closes, zero bytes back
- malformed frame :: socket closes, zero bytes back
- socket missing :: connection fails, and this is the one case Emacs can detect

* What This Buys

- The paste, the carriage return, and the terminal all disappear. The submit
  race in [[file:./02-paste-submit-reliability.org][Paste Submit Reliability]]
  cannot happen.
- The at-mention expansion in
  [[file:./03-relay-must-not-read-files.org][Relay Must Not Read Files]] cannot
  happen either, because nothing is typed into an input box. Both guards there
  become unnecessary rather than merely sufficient.
- Delivery is addressed by PID, so the relay cannot misroute. It has done so:
  asked for =byohctl-ci-integration=, it sent to =byohctl-teamcity-integration=.
- The coordinator session, its startup command, the =DO_NOT_TRACK= workaround,
  and the start and clear commands all go away.

* Confirming A Send

Nothing is written back on the connection itself, so a bare send tells Emacs
only that a live socket accepted some bytes. Status arrives out of band instead,
and this now works end to end.

Emacs binds its own socket, names it in the =from= field, and the receiver opens
a fresh connection to it to report what happened. Verified live:

- Bind a listening socket inside =/tmp/cc-socks/=. The receiver vets the
  namespace, not the filename: =emacs-bridge-receipt.sock= was accepted, so the
  name does not have to look like =<pid>.sock=.
- Send =from= as =uds:= followed by the percent-encoded socket path, and a
  =msg_id= UUID to correlate with.
- A failing target connects back within seconds and writes one
  =peer_message_status= frame carrying =orig_msg_id= and a reason written for a
  human to read.

Observed frames:

- Held target :: =status: held=, reason naming the recipient's approval step.
- Refusing target :: =status: expired=, =status_detail: refused=, reason
  explaining the recipient is not accepting cross-session messages.

** Receipts only ever report failure

A =delivered= status exists but reaches a sender on one path only: a message
that was held, and that the recipient's user then approved. A message accepted
straight away produces no receipt at all. The accept branch of the inbound gate
returns without emitting one. Six accepted sends across both priorities, with
and without =msg_id=, to idle and busy targets, produced zero frames.

So receipts are a negative acknowledgement and cannot be the success signal.
There is a better one.

** Drops are reported, and one of them will happen in normal use

=dropped= frames arrive fast, correlate by =orig_msg_id=, and carry a
=drop_reason=. The reasons are =duplicate=, =rate-limited=, =queue-full=,
=hop-loop= and =hop-runaway=.

=duplicate= is the one that matters here. Identical content from the same sender
within 30 seconds is dropped and never delivered. Sending the same instruction
about the same lines twice in quick succession is an ordinary thing to do, so
the bridge has to surface this rather than let it look like success.

Other defaults worth knowing: sustained rate is one message every two seconds
with a burst of thirty, and fifty undelivered peer messages fills the queue. The
first drop in a sixty-second window is reported immediately; further drops are
batched and arrive about five seconds later in one frame whose =dropped_msg_ids=
names them.

* Confirming Success

The receiving session writes a line to its own transcript when a message is
queued. That line is the success signal.

#+begin_example
{"type":"queue-operation","operation":"enqueue","timestamp":"...",
 "sessionId":"...","content":"<the exact text that was sent>"}
#+end_example

- Path :: =~/.claude/projects/<slug>/<sessionId>.jsonl=, where =sessionId= comes
  from the session registry and =slug= is the session's =cwd= with every
  character outside =[A-Za-z0-9]= replaced by a dash. If that path is absent,
  glob =~/.claude/projects/*/<sessionId>.jsonl= before concluding anything.
- Correlation :: by exact =content= match. The record carries no =msg_id=. The
  matching =dequeue= line has no content at all.
- Meaning :: the line is written after admission, so its presence means the
  message cleared the accept gate and the duplicate, rate and queue guards. It
  is in the queue.
- Timing :: the timestamp lands 1 to 18 ms after the send, and the writer
  flushes on a 100 ms interval, so budget around 150 ms before it is readable.

It can be absent for reasons that are not failure: transcript persistence turned
off, history suppression, or a session so newly started that its file does not
exist yet. Absence therefore means unconfirmed, not failed.

* Knowing When The Target Finished

Separate from delivery, a sender can ask to be told when the target next goes
idle. Send a control frame:

#+begin_example
{"type":"control","action":"notify_when_idle","msgV":1,
 "msg_id":"<uuid>","from":"uds:<path>"}
#+end_example

A =peer_idle_notice= comes back with =state= of =idle=, =exited= or
=unavailable=, and =finished_at=. It fires once, 750 ms after the target's queue
drains, so it means finished rather than briefly between tokens. Session death
reports =exited= within milliseconds.

The sharp edge: subscribing to an already idle target fires immediately, about a
turn that ended before the subscription. Compare =finished_at= against the send
time. Greater means a turn ended after the message. Anything else means the
session was already idle and the message has not been worked through.

Subscribe after sending, never before, or an idle target answers about the wrong
turn. The target also tells its own user that something asked to be notified, so
this is visible rather than silent.

* Settled Design

- Discovery reads =~/.claude/sessions/*.json=. It is no longer a preference: the
  transcript path needs =sessionId= and =cwd=, and the idle subscription needs
  =peerFeatures=. Only the registry carries them. It also drops a subprocess
  from every send.
- The wait for confirmation is 500 ms, roughly three times the worst measured
  latency, with room for a loaded machine.
- A send reports one of three outcomes. Transcript line found means delivered.
  A status frame means failed, and its =reason= is already written for a human
  to read. Neither means sent but unconfirmed, which is stated plainly rather
  than dressed up as either.

* Open Questions

- What owns the receipt socket's lifetime. It has to be bound while a send is in
  flight, cleaned up afterwards, and cope with a stale file left by an Emacs
  that crashed.
- Whether a =bypassPermissions= target holds the message. The docs say it does.
  Untested, because starting one needs an interactive security confirmation that
  was not authorised. The =hold= case produces the same frame, so this is
  unlikely to change the design.
- Whether the relay path has been silently hitting the duplicate guard all
  along. The coordinator sends through the same mechanism, so a repeated
  instruction within thirty seconds would be dropped there too, and nothing in
  the current bridge would notice.

* Scope

The bridge is in daily use. That constrains this work more than anything else
in the plan.

The relay stays the default. The socket path goes in behind an option that is
off unless asked for, and the default only changes once the socket path has been
tested properly and carried real traffic. A working setup does not get swapped
out for an untested one.

Development must not disturb the running coordinator or any live session.
Experiments use throwaway sessions in a scratch directory, started and killed by
the test itself, and never write to a socket belonging to a session someone is
using.

Nothing about the coordinator is deleted in this work. Removing it is a cleanup
task for later, listed below so it is not lost, and so nobody mistakes the
leftover relay code for something still load-bearing.
